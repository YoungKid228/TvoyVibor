**Факт.** Уже реализовано и **переиспользуемо** для новой игры:

## 2. Используемые технологии и архитектура

### 2.1 Решение по движку (главное архитектурное решение)

ТЗ (п. 11) предпочитает Phaser 3. **Предложение: Phaser не вводить.** Обоснование:

1. «Проверь свой бюджет» — пошаговая сюжетная игра с карточками решений и расчётом бюджета, а не real-time-сцена с физикой/спрайтами. Решающий слой — бизнес-логика и DOM-интерфейс, а не рендер-цикл.
2. В репозитории уже есть React 18 + Tailwind 4 + пиксель-UI-кит, согласованный с визуальным стилем проекта. Введение Phaser означало бы второй UI-стек, дублирование PWA-конфигурации и второй цикл рендера.
3. ТЗ прямо запрещает менять существующие технологии без обоснования (п. 11) и требует сначала оценить возможность повторного использования (п. 12).
4. Требование «60 FPS» (п. 14) для игры без непрерывной анимации выполняется тривиально.

**Предложение.** Реализовать игру как React-приложение поверх существующей инфраструктуры, с чистым модулем доменной логики в `src/lib/`, тестируемым без DOM.

**Вопрос 1.** Утвердить отказ от Phaser 3 (или обосновать его ввод, если заказчик настаивает на «2D-графике с игровым движком» буквально).

### 2.2 Архитектура

```
src/
  budget/                       # новая вертикаль игры, изолирована от профориентации
    data/
      scenario.ts               # сценарий: раунды, варианты, цены, тексты (типизированные константы)
      recommendations.ts        # правила рекомендаций (детерминированные)
    core/
      types.ts                  # GameState, FinanceSnapshot, Decision, RoundId
      finance.ts                # ЧИСТАЯ финансовая логика (без DOM/React)
      evaluation.ts             # шкала оценки результата
      recommendations.ts        # подбор рекомендаций по состоянию
      reducer.ts                # игровой процесс: переходы, идемпотентность, валидация
    storage/
      db.ts                     # IndexedDB-обёртка (обёртка над window.indexedDB, без зависимостей)
      saveRepository.ts         # сохранение/восстановление + версия схемы
    state/
      BudgetGameContext.tsx     # React-контекст поверх reducer'а
    components/                 # экраны и карточки игры
    pages/
      BudgetGamePage.tsx        # корневой экран игры (роутинг внутри игры)
```

**Принципы (из п. 12 ТЗ):**
- `core/finance.ts` — единственное место, где считаются деньги. Не зависит от React, DOM, `window`.
- Все данные сценария — в `scenario.ts` как типизированные константы; цены и тексты меняются без правки логики.
- `core/reducer.ts` — единственное место смены состояния; все действия идемпотентны (повторное применение того же решения не меняет баланс).
- Формат сохранения: `{ schemaVersion, state, updatedAt }`.

**Предложение (обоснование IndexedDB).** ТЗ (п. 10) требует IndexedDB. В проекте используется `localStorage`. Варианты:
- **(A) Реализовать IndexedDB** (~120 строк, обёртка + миграции) — соответствует ТЗ, но дублирует `storage.ts`.
- **(B) Оставить `localStorage`** — проще, но формально нарушает п. 10.

**Предложение:** вариант **(A)** с тонкой обёрткой `db.ts` (без новых зависимостей, `idb`-пакет не добавляем), т.к. требование зафиксировано явно, а `localStorage` не масштабируется и является синхронным. Существующий `src/lib/storage.ts` **не трогаем** — он обслуживает профориентацию.

**Вопрос 2.** Подтвердить переход на IndexedDB для игры (при сохранении `localStorage` для существующих тестов).

## 5. Предлагаемая архитектура

### 5.1 Модель состояния

```ts
type RoundId = "menu" | "round1" | "round2" | "birthday" | "summary";

type GameState = {
  schemaVersion: number;
  screen: RoundId;
  capital: number;          // 20 000
  salaryApplied: boolean;  // зарплата 15 000 начислена ровно один раз
  mandatorySpent: number;  // 14 000
  entertainmentSpent: number;
  phoneSpent: number;
  birthdaySpent: number;
  savings: number;         // 0 | 2000 | 4000
  completed: Record<RoundId, boolean>; // идемпотентность: раунд нельзя применить дважды
};
```

### 5.2 Финансовые формулы (п. 6 ТЗ, без изменений)

```
totalIncome   = 20 000 + 15 000 = 35 000
totalExpenses = 14 000 + entertainment + phone + birthday
finalBalance  = 35 000 − totalExpenses
```
**Накопления не вычитаются из итогового остатка** — они показываются отдельной строкой («предложено отложить»). Это согласуется с контрольным сценарием: расходы 21 300, остаток 13 700 — накопления в формуле отсутствуют. **Вопрос 4** (см. раздел 7) — подтвердить трактовку.

### 5.3 Границы и защита от недопустимых операций (п. 6)

- `savings ≤ available` (available = 35 000 − totalExpenses на момент раунда 1);
- выбор развлечений — мультивыбор с суммированием стоимости;
- раунд/событие применяется один раз (`completed[round]` guard);
- `salaryApplied` — зарплата начисляется один раз;
- каждая стоимость списывается **один раз** — стоимость берётся из сценария по id варианта, а не из ввода пользователя;
- при нехватке средств — расчёт возвращает `ok: false` с понятным сообщением, состояние не мутируется.

### 5.4 Оценка (п. 7)

| Итоговый остаток | Результат |
|---|---|
| ≥ 7 000 | Отличный результат |
| 3 000 – 6 999 | Хороший результат |
| 0 – 2 999 | Есть над чем поработать |
| < 0 | Бюджет ушёл в минус |

Каждому диапазону — текстовое объяснение.

### 5.5 Рекомендации (п. 8)

Набор детерминированных правил, каждое — `{ id, when(state, result), text }`:
- `savings-is-zero` — накопления не созданы → «создайте финансовый резерв»;
- `no-entertainment` — отказ от развлечений → про баланс и качество жизни;
- `entertainment-heavy` — сумма развлечений > 3 000 → «планируйте необязательные расходы»;
- `new-phone` — покупка нового телефона (12 000) → «сравните ремонт и покупку»;
- `repair-phone` — ремонт → «иногда ремонт выгоднее»;
- `spare-phone` — запасной телефон → «работоспособность без затрат»;
- `big-gift` / `small-gift` / `symbolic-gift` — варианты подарка → разные формулировки;
- `savings-high` — накопления ≥ 2 000 → «резерв сформирован»;
- базовые правила по приоритету обязательных расходов и оценке последствий решений.

Правила применяются по фиксированному порядку; итог — до 4–5 пунктов.

### 5.6 Сохранение

```ts
type SaveEnvelope = { schemaVersion: 1; state: GameState; updatedAt: string };
```
Запись в IndexedDB (`db = "tvoy-vibor"`, `store = "budget-saves"`, `key = "current"`). При `schemaVersion` ниже текущей — сохранение считается несовместимым и предлагается сброс с подтверждением.

### 5.7 PWA

Требуемые изменения в `vite.config.ts`:
- добавить в `workbox.globPatterns` расширения `png|webp|svg` (иконки уже в `public/icons` — сейчас кэшируются только `svg`),
- `manifest.name`/`short_name` — «Проверь свой бюджет» (или «Твой выбор: Проверь свой бюджет»),
- `start_url`/`scope` — `/budget-game/` (отдельная точка входа),
- `theme_color`/`background_color` — согласовать палитру игры.

**Q1 (⛔, п. 11).** Использовать Phaser 3 или реализовать игру на существующем React-стеке?
Предложение: React + существующий UI-кит, Phaser не вводить (раздел 2.1). От ответа зависит объём задач по рендерингу.

**Q2 (⛔, п. 10).** Подтверждаем IndexedDB для сохранения игры? Предложение: да, новая тонкая обёртка, `localStorage` в существующем коде не трогаем.

**Q3 (не блокирует).** Нужна ли игра **отдельным PWA** (свой `start_url`, имя в манифесте, своя иконка) или как раздел внутри существующего PWA «Твой выбор»? Предложение: раздел внутри (проще, один SW/манифест), название игры — заголовок раздела.

**Q4 (⛔, п. 6).** Как учитывать накопления (0 / 2 000 / 4 000 ₽)?
Предложение (согласовано с контрольным сценарием): накопления — **отложенная часть остатка**, они **не вычитаются** из итогового остатка и отображаются отдельной строкой. Требуется подтверждение, а также ответ: показываются ли накопления как часть «доступных средств» в раундах 2–3 (предложение: нет, доступные средства = остаток − уже отложенное, накопления «заморожены»).

**Q5 (⛔, п. 6).** Что делать при нехватке средств (например, ремонт 4 000 при доступных 2 000)?
Предложение: показывать предупреждение и требовать явного подтверждения; отрицательный остаток допустим (шкала результата это предусматривает). Альтернатива: блокировать выбор.

**Q6 (⛔, п. 5.2).** Обязательные расходы 14 000 ₽ фиксированы всегда, или игрок может влиять на их состав? В ТЗ приведены только суммы без вариантов. Предложение: фиксированы.

**Q7 (не блокирует, п. 5.2).** Можно ли выбрать **несколько** развлечений одновременно (кино + бар + клуб)? ТЗ: «один, несколько или ни одного» — подтверждаем, что складываем стоимости и ограничиваем суммарно остатком.

**Q8 (не блокирует, п. 5.2).** Варианты накоплений 0 / 2 000 / 4 000 ₽ — фиксированный список или свободная сумма? Предложение: фиксированный список (как в ТЗ).

**Q9 (не блокирует, п. 5.2).** Когда начисляется зарплата 15 000 ₽? ТЗ: «после завершения первого раунда». Предложение: начисляется при переходе из раунда 1 в раунд 2 (один раз, флаг `salaryApplied`), иначе в раунде 1 баланс отрицательный.

**Q10 (не блокирует, п. 5.3).** Нужны ли тексты «преимуществ/недостатков» и «влияния на баланс» для каждого варианта решения (ТЗ п. 5.3 требует показать)? В ТЗ самих текстов нет. Предложение: подготовить редакционные тексты и вынести на согласование; либо использовать краткие шаблоны.

**Q11 (не блокирует, п. 7–8).** Утвердить финальные тексты: 4 объяснения результата и 8–10 рекомендаций. Предложение: подготовить черновик, согласовать тональность (мотивирующая, без морализаторства).

**Q12 (не блокирует, п. 10).** Проверять ли обновление Service Worker так, чтобы игра не ломалась на середине сессии? Предложение: `autoUpdate` + сохранение в IndexedDB обеспечивает безопасное восстановление.
