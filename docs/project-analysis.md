## 6. Методика подсчёта: что есть и что решено

**В docx:** каждый тест привязан к одной профессии; результат — сумма по шкале 1–5 и пороговые интерпретации. Эти тексты написаны под модель «один тест = одна профессия» и под вопросные объёмы 10/15.

**В техдокументации (и подтверждено пользователем):** один тест даёт баллы по нескольким профессиям; итог — нормированный процент соответствия по каждой профессии, показываются наиболее и наименее подходящие с объяснением. Процент трактуется как показатель соответствия модели теста, не как научный прогноз.

**Принятые пользователем решения (фиксируются как требования):**
1. Объём опубликованного теста — ровно 20 вопросов.
2. Методика — мультипрофессиональная: варианты ответов раскладывают баллы по нескольким профессиям (схема `scores: Record<professionId, number>` из техдокументации).
3. Финальные тексты вопросов и раскладку баллов составляет агент на основе образцов docx (вопросы в docx — примерные). Содержательное согласование методики с постановщиком задачи до публикации остаётся желательным.

**Не определено ни в одном источнике (нужно решить до Task 10 плана):**
- правила ничьих в итоговом рейтинге профессий (предложение в плане: стабильный порядок по `professions.json`);
- поведение при пропущенных ответах (предложение: вопрос исключается из суммы и из максимума);
- какие профессии входят в модель каждого теста и какова раскладка баллов в опциях.

## 7. Требования к MVP

Источники: `TECH_STACK_PGU_Economics_PWA.md` (разделы 1, 6, 7, 8, 13) + решения пользователя.

### Функциональные
1. Выбор направления подготовки и варианта теста по аудитории: школьники / СПО-бакалавриат-магистратура.
2. Тест: ровно 20 вопросов, отображение прогресса, переход к предыдущему вопросу без потери ответа.
3. Подсчёт по мультипрофессиональной модели: суммирование баллов, нормализация к достижимому максимуму, сортировка профессий.
4. Экран результата: наиболее и наименее подходящие профессии + объяснение, на основании чего сформирован результат (формулировка «соответствие модели теста»).
5. Сохранение прогресса локально: testId, ответы, номер вопроса, дата изменения; предложение продолжить при повторном открытии; предупреждение перед очисткой прогресса.
6. Описания профессий (из Блока 1/2 docx) доступны в контексте результата; зарплатные данные ЕАО — опционально в карточке профессии на экране результата.

### PWA
7. Манифест: `name`, `short_name`, `start_url`, `scope`, `display: standalone`, цвета темы, иконки 192/512 (+ maskable).
8. Service Worker кэширует оболочку; приложение работает офлайн после первой загрузки; обновление SW не теряет ответы.
9. Обычный браузер — экран-инструкция установки (Windows/macOS/Android/iOS) с запасным сценарием «продолжить в браузере»; standalone — сразу тесты. Определение — `matchMedia("(display-mode: standalone)")` + `navigator.standalone`; это UX-ограничение, не защита доступа.

### Данные
10. Данные в JSON: `directions.json`, `professions.json`, `tests.json`; схема по техдокументации (`Audience`, `AnswerOption`, `Question`, `CareerTest`, `Profession`).
11. Автоматическая валидация перед публикацией: ровно 20 вопросов, уникальность всех id, существование профессий из `scores`, покрытие обеих аудиторий, ≥2 опции у вопроса.

### Дизайн и доступность
12. Mobile-first от 320 px, без горизонтальной прокрутки; академично-дружелюбный стиль; ограниченная палитра (брендбук ПГУ не предоставлен — см. пробелы).
13. Клавиатурная навигация, видимый фокус, контраст ≥4.5:1, подписи элементов форм, `prefers-reduced-motion`, интерактивные зоны ≥44 px.

### Стек и тестирование
14. React + TypeScript + Vite + Tailwind CSS + vite-plugin-pwa (Workbox) + Vitest + Playwright; деплой — статика на Vercel (`npm run build` → `dist`).
15. Проверки перед публикацией — по разделу 10 техдокументации (функциональные, PWA, доступность).

### Вне MVP
БД, админ-панель, аккаунты, серверная аналитика, синхронизация между устройствами, редактирование тестов через UI, серверная защита JSON, научная валидация методики.

## 8. Недостающие данные и пробелы

**Контент (блокирует Task 10 плана, компенсируется авторской работой агента):**
1. Вопросы в docx — примерные и написаны под 10/15 вопросов; для формата «ровно 20» финальные вопросы нужно составить заново на основе образцов.
2. Раскладка баллов опций по профессиям (мультипрофессиональная модель) в исходниках отсутствует полностью — её нужно спроектировать.
3. Тест для «специалиста по закупкам» — отсутствует; тест «экономист (взрослые)» — без вопросов; «специалист по бюджетированию» — без теста и карточки. В MVP достаточно одного теста на аудиторию; вопрос включения этих профессий в модель подсчёта — открытый.
4. Школьный тест «экономист» задвоен (в обоих экземплярах одинаковый текст).
5. Карточек нет для «экономиста» и «специалиста по бюджетированию».

**Методика:**
6. Правила ничьих и пропущенных ответов не определены (в техдокументации требуется определить заранее; предложения зафиксированы в п. 6).

**Брендинг и материалы:**
7. Брендбук/палитра ПГУ не предоставлены — палитра берётся нейтральная до предоставления.
8. Логотип и иконки приложения отсутствуют — на реализацию ставятся placeholder-иконки.
9. Значение отметок «+» и номера направлений у профессий в Блоке 1 не расшифрованы — при генерации данных не используются.
10. Целевая ссылка/домен и имя GitHub-репозитория для деплоя не определены.

**Технические ограничения (известные, не блокируют):**
11. Браузеры не дают надёжного универсального определения установки PWA — применено UX-ограничение (п. 9 требований).
12. Офлайн-доступность зависит от браузера/режима экономии данных — проверяется на целевых устройствах.
