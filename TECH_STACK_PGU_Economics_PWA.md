# Техническая документация

## PWA «ПГУ: Экономика --- твой выбор»

**Версия документа:** 1.0\
**Статус:** проектирование первой версии\
**Назначение:** профориентационные тесты по профессиям и направлениям
подготовки.

------------------------------------------------------------------------

## 1. Цели первой версии

Первая версия приложения включает только блок профориентационных тестов.

Функциональность:

-   выбор направления подготовки;
-   выбор варианта теста: для школьников или для выпускников СПО /
    бакалавриата;
-   20 вопросов в каждом тесте;
-   группировка вопросов по профессиям внутри выбранной сферы;
-   отображение прогресса и возможность вернуться к предыдущему вопросу;
-   подсчёт результатов по профессиям;
-   показ наиболее и наименее подходящей профессии;
-   локальное сохранение прогресса на устройстве;
-   установка в виде PWA и кэширование ресурсов для работы без сети
    после первой загрузки;
-   экран-инструкция при открытии обычной ссылки, если приложение
    запущено в браузере.

Содержимое каталога `Proektnaya_deyatelnost` является исходным
материалом. До изучения файлов не следует придумывать направления,
профессии, вопросы или методику оценки.

## 2. Технологический стек

  Технология        Назначение
  ----------------- ------------------------------------------------------
  React             Компонентный пользовательский интерфейс
  TypeScript        Типизация данных, ответов и результатов
  Vite              Локальная разработка и сборка статических файлов
  Tailwind CSS      Адаптивные стили и дизайн-система
  vite-plugin-pwa   Генерация PWA-манифеста и настройка Service Worker
  Workbox           Стратегии кэширования ресурсов
  JSON              Статические данные направлений, профессий и вопросов
  localStorage      Небольшие данные о прогрессе на устройстве
  Vitest            Модульные тесты логики подсчёта
  Playwright        Сквозные тесты пользовательских сценариев
  Git + GitHub      Контроль версий и резервная копия исходного кода
  Vercel            HTTPS-хостинг и автоматические деплои

### Почему этот стек

Приложение не требует серверной бизнес-логики, пользовательских
аккаунтов или общей базы данных. Поэтому клиентская архитектура на
React + Vite проще и дешевле в сопровождении, чем полноценный серверный
фреймворк.

Публикация на Vercel возможна как статический сайт. Условия бесплатного
тарифа и правила коммерческого использования нужно проверить перед
запуском официального университетского проекта.

## 4. Структура данных

Данные тестов хранятся в JSON и поставляются вместе с приложением.
Пример схемы --- иллюстративный; реальные вопросы и профессии нужно
взять из материалов проекта.

``` ts
type Audience = "school" | "college_or_bachelor";

type AnswerOption = {
  id: string;
  label: string;
  scores: Record<string, number>;
};

type Question = {
  id: string;
  text: string;
  professionGroupId: string;
  options: AnswerOption[];
};

type CareerTest = {
  id: string;
  directionId: string;
  audience: Audience;
  title: string;
  questionIds: string[];
};

type Profession = {
  id: string;
  directionId: string;
  title: string;
  description: string;
};
```

Требования к данным:

-   в каждом опубликованном тесте ровно 20 вопросов;
-   идентификаторы вопросов, вариантов ответа и профессий уникальны в
    пределах соответствующих наборов;
-   каждый идентификатор профессии в `scores` должен существовать;
-   для обеих аудиторий должны быть явно определены доступные тесты;
-   данные проверяются автоматическим тестом перед публикацией.

## 5. Методика подсчёта результата

Профориентационный тест не должен трактовать ответы как экзаменационные
«правильно/неправильно», если исходная методика этого не
предусматривает.

Рекомендуемая модель:

1.  Каждый вариант ответа задаёт баллы для одной или нескольких
    профессий.
2.  После прохождения суммируются баллы по каждой профессии.
3.  Если у профессий различаются максимально возможные баллы, результат
    нормализуется относительно достижимого максимума.
4.  Профессии сортируются по итоговому показателю.
5.  Показываются наиболее и наименее подходящие профессии с объяснением
    результата.

Процент следует обозначать как показатель соответствия модели теста, а
не как научно доказанную вероятность профессионального успеха.

Нужно заранее определить правила для ничьих и пропущенных ответов. Если
исходные материалы не содержат методики, её необходимо согласовать до
написания тестов. Не следует автоматически придумывать психологические
выводы.

## 6. PWA и экран установки

### Требования

-   приложение работает по HTTPS;
-   в Web App Manifest заданы `name`, `short_name`, `start_url`,
    `scope`, `display: "standalone"`, цвета темы и иконки необходимых
    размеров;
-   Service Worker кэширует оболочку приложения и необходимые
    статические ресурсы;
-   приложение корректно сообщает о недоступности сети;
-   обновление Service Worker не должно приводить к потере текущих
    ответов;
-   предусмотрены инструкции для Windows, macOS, Android и iOS.

### Ограничение определения установки

Браузеры не предоставляют универсального, полностью надёжного способа
определить факт установки PWA во всех операционных системах и браузерах.
Можно проверять режим запуска через
`window.matchMedia("(display-mode: standalone)")`, а в поддерживаемых
браузерах дополнительно учитывать платформенные признаки.

Это не является защитой доступа. Пользователь всё ещё может открыть
отдельные маршруты напрямую или использовать браузер, где признак
установки недоступен. Если обязательна настоящая защита, потребуется
серверная проверка, но она не входит в текущую архитектуру без backend.

Для требования проекта применяется UX-ограничение: обычный режим
браузера показывает экран установки, а standalone-режим показывает
тесты. На неподдерживаемых устройствах должна быть понятная инструкция и
согласованный запасной сценарий.

### Offline

После успешной первой загрузки кэшированные файлы приложения могут
открываться без сети. Однако очистка кэша, режимы экономии данных и
особенности конкретного браузера могут повлиять на офлайн-доступность.
Офлайн-режим нужно проверить на целевых устройствах.

## 7. Сохранение данных

`localStorage` подходит для небольшого прогресса:

-   ID теста;
-   выбранные ответы;
-   текущий номер вопроса;
-   дата последнего изменения.

Не хранить в `localStorage` пароли, секреты или чувствительные
персональные данные. Локальные данные могут быть удалены пользователем
или браузером и не синхронизируются между устройствами.

Если сохранение не требуется, можно хранить состояние только в памяти.
Перед очисткой прогресса следует предупреждать пользователя.

## 8. Требования к дизайну

Визуальное направление: современный университетский продукт,
академичный, дружелюбный и уверенный.

-   mobile-first: сначала проектировать для смартфона;
-   ясная типографическая иерархия и комфортная длина строки;
-   ограниченная палитра, согласованная с официальным стилем ПГУ, если
    брендбук доступен;
-   повторно используемые компоненты и дизайн-токены;
-   заметный прогресс теста и понятное состояние выбранного ответа;
-   крупные интерактивные области и доступный контраст;
-   анимации короткие и необязательные;
-   учитывать `prefers-reduced-motion`;
-   не использовать декоративные графики, имитирующие научную точность
    результатов.

Рекомендуемые дизайн-задачи для AI Skills: `frontend-design`,
`ui-ux design`, `responsive design`, `web accessibility`,
`microinteractions`. Названия конкретных Skills нужно проверить в
каталоге используемого AI-агента.

## 9. MCP и инструменты разработки

MCP --- это инструменты, которыми AI-агент пользуется во время
разработки; они не являются частью приложения для конечного
пользователя.

  -----------------------------------------------------------------------
  Инструмент                          Зачем
  ----------------------------------- -----------------------------------
  Filesystem MCP                      Читать материалы
                                      `Proektnaya_deyatelnost` и
                                      редактировать файлы проекта

  Playwright MCP                      Проверять сценарии в реальном
                                      браузере

  GitHub MCP                          Работать с репозиторием,
                                      изменениями и issues

  Context7 MCP                        Получать актуальную документацию
                                      библиотек, если доступен в среде
  -----------------------------------------------------------------------

Минимально достаточно файлового доступа к папке проекта и браузерного
тестирования. Доступ к файловой системе нужно ограничить каталогом
проекта.

## 10. Тестирование перед публикацией

### Функциональные проверки

-   каждый тест содержит ровно 20 вопросов;
-   доступны две аудитории;
-   переходы вперёд и назад работают корректно;
-   выбранный ответ сохраняется при переходе между вопросами;
-   результат учитывает все ответы;
-   сортировка профессий корректна;
-   ничьи обрабатываются предсказуемо;
-   отсутствующие или повреждённые данные не ломают приложение.

### PWA-проверки

-   манифест доступен и валиден;
-   иконки корректны;
-   приложение устанавливается на поддерживаемых устройствах;
-   обычная ссылка показывает экран-инструкцию;
-   standalone-запуск показывает тесты;
-   повторное открытие работает без сети после предварительного
    кэширования;
-   обновление версии приложения не теряет ответы неожиданным образом.

### Проверки доступности и интерфейса

-   мобильная ширина от 320 px;
-   клавиатурная навигация;
-   видимый фокус;
-   достаточный контраст;
-   доступные подписи элементов формы;
-   понятные сообщения об ошибках;
-   отсутствие горизонтальной прокрутки на типовых экранах.

## 11. Сборка и публикация

Типовой процесс:

1.  Установить поддерживаемую LTS-версию Node.js.
2.  Установить зависимости через пакетный менеджер проекта.
3.  Запустить режим разработки.
4.  Выполнить модульные и браузерные тесты.
5.  Собрать production-версию.
6.  Проверить содержимое каталога сборки локально.
7.  Загрузить проект в GitHub.
8.  Подключить репозиторий к Vercel.
9.  Указать команду сборки `npm run build` и каталог результата `dist`.
10. Проверить HTTPS, установку PWA, маршрутизацию и офлайн-поведение на
    целевых устройствах.

Конкретные версии библиотек следует фиксировать в `package.json` и
lock-файле. Перед началом разработки проверяйте совместимость актуальных
версий React, Vite и `vite-plugin-pwa`.

## 12. Что не входит в первую версию

-   база данных;
-   админ-панель;
-   аккаунты и авторизация;
-   серверная аналитика;
-   синхронизация результатов между устройствами;
-   редактирование тестов через интерфейс;
-   серверная защита тестов от просмотра исходных JSON;
-   научная валидация профориентационной методики.

Все статические данные, отправленные в браузер, технически доступны
пользователю. Поэтому нельзя размещать в JSON секреты или рассчитывать
на конфиденциальность вопросов.

## 13. Критерии готовности первой версии

Первая версия готова, когда пользователь может:

1.  Установить PWA на поддерживаемом устройстве.
2.  Открыть приложение в standalone-режиме.
3.  Выбрать направление и вариант теста.
4.  Ответить на 20 вопросов.
5.  Вернуться к предыдущим вопросам без потери ответов.
6.  Увидеть наиболее и наименее подходящие профессии.
7.  Понять, на основании чего сформирован результат.
8.  Повторно открыть приложение и продолжить тест, если прогресс
    сохранён.
9.  Использовать ранее кэшированное приложение без сети в пределах
    возможностей браузера.
